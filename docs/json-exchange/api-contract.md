# Структуры JSON и расширение family banking MVP

Актуализация: 21.10.2026. Действующие маршруты, режим запуска, проверки доступа
и ошибки описаны в [основном API-контракте](../api-contract.md). Работают health,
демо-пользователи, разрешённые счета, история, переводы родителя и копилки.
Детская привязка и участие семьи реализованы: новые команды, `PigView`, квитанция
чужому ребёнку и запросы родителю описаны в [контракте копилок](../piggy-banks.md).
Этот файл сохраняет полный исходный договор DTO; наличие поля в нём не означает
готовность всех учебных, игровых функций и расписания.
Настоящая аутентификация и открытие банковских счетов не реализованы.
Существующие названия из `structure.txt` сохранены, включая опечатки.
Все данные и ID в примерах вымышлены. `limit: 15000` — демонстрационная настройка,
а не утверждение о законодательно установленном пороге.

## 1. Как идёт обмен

```text
Форма Vue / Pinia
  → обычный JS-объект
  → uni.request: объект data → HTTP JSON
  → FastAPI: JSON → входная Pydantic-схема
  → сервис: права, остаток, заморозка, лимит, транзакция БД
  → отдельная публичная Pydantic-схема → HTTP JSON
  → uni.request: JSON → объект res.data
  → обновление состояния экрана / Pinia
```

JSON-файл не передаётся при каждой операции. Файлы в `examples/` — общие
примеры и тестовые данные, которые можно открыть обоим разработчикам.

- Базовый адрес: `http://<BACKEND_LAN_IP>:8000/api/v1`; реальный IP нужно подставить.
- Тела запросов/ответов: JSON UTF-8, `Content-Type: application/json`.
- Ответ ресурса — сам объект, без обёртки `data`.
- Ответ списка: `{ "items": [...] }`.
- `res.data` — имя свойства uni.request, а не дополнительный ключ в JSON сервера.
- Для GET тело не передаём; история принимает query-параметры `limit` и `offset`.
- Ошибки определяем по HTTP-статусу. Callback `success` не означает статус 2xx.

В H5 origin frontend должен быть явно разрешён в CORS backend.
На другом компьютере и телефоне `localhost` обозначает само это устройство.
Схема аутентификации пока не реализована. Включённый `DEMO_MODE` выбирает
пользователя через `DEMO_USER_ID=10` либо явный демонстрационный заголовок
`X-Demo-User-Id`. Это не подтверждение личности. Сервис проверяет существование
родителя и принадлежность обоих счетов. Реальные данные и деньги не используются.

## 2. Общие типы

| Значение | JSON-тип и правило |
| --- | --- |
| ID | Положительное целое число, не строка и не имя пользователя |
| Суммы BYN | Целое число копеек: `2500` = 25,00 BYN |
| MT | Отдельное неотрицательное целое число, не входит в денежные остатки |
| Числа | В пределах безопасного целого JavaScript: до 9007199254740991 |
| Флаг | `true` / `false`, не `0` / `1` и не строки |
| Нет значения | `null`; поле остаётся в ответе |
| Нет элементов | `[]`, не `null` |
| Период | `"daily"`, `"weekly"`, `"monthly"` |
| Возрастная группа | `"children"`, `"teanagers"`, `"adult"`; написание `teanagers` сохраняется |
| Ключи вопросов | Строки `"1"`, `"2"`; ключи JSON-объекта всегда строки |
| Индекс ответа | Целое число с нуля: первый вариант = `0` |

Согласованные имена новых полей: `tamagochi.name`, `Account.limit`,
`Account.limit_period`, `Test.reward_MT`, `News.text`,
`AutoTransaction.source_account_id`.

**Предложение формата для дат:** все три поля `data` — ISO 8601 со временем
и часовым поясом. В ответах сервер нормализует их в UTC, например
`"2026-10-20T10:30:00Z"`. В запросе допустим явный offset, например `+03:00`.
Дата без времени/смещения не принимается этими демонстрационными схемами.

| Поле | Смысл |
| --- | --- |
| `Transaction.data` | Время операции; назначает сервер |
| `Parent_Task.data` | Точный срок выполнения; frontend должен явно передать время |
| `AutoTransaction.data` | Начальный момент расписания, от которого считаются периоды |

Не превращаем выбранную пользователем календарную дату в полночь молча.
Календарные денежные лимиты действующего API считаются по UTC+03: день с 00:00,
неделя с понедельника, месяц с первого числа. Поведение месячного расписания
для 29–31 числа ещё нужно закрепить; автопереводы не реализованы.
Сам сериализатор лимиты и расписания не вычисляет.

## 3. Публичные объекты

**Списки связей содержат только ID**, а не смесь чисел и объектов.
Полные данные получаются отдельным запросом. Это предотвращает циклическое
вложение User → Account → User. Локальный `entities.json` содержит все объекты
по именам классов для проверки; такой общий endpoint не реализован.

### User

`id`, `login`, `role`, `accounts: number[]`, `ECOfamily_id: number|null`,
`newses_id: number[]`, `test_id: number[]`, `auto_transaction: number[]`.

`role`: `parent` или `child`. Семья одна. `accounts` содержит счета, владельцем
которых является пользователь; это не универсальный список разрешённых ему счетов.
`newses_id` — прочитанные статьи, `test_id` — завершённые тесты,
`auto_transaction` — ID привязанных автопереводов.

В текущем `/me` поля `ECOfamily_id`, `newses_id`, `test_id`, `auto_transaction`
возвращаются как `null`, `[]`, `[]`, `[]`: соответствующие функции ещё не
сохраняются в БД. Остальные поля загружаются из действующей демонстрационной БД.

`password` отсутствует в ответе всегда. Отдельный входной запрос аутентификации
будет согласован при её реализации. Нельзя сериализовать ORM через `__dict__`.

### ChaildProfile

`user_id`, `parent_id`, `age_group`,
`agree_parent: { pig: boolean, history: boolean, transaction: boolean }`,
`tamagochi: { name: string, eat: number, room: number, cloth: number }`, `MTcount`.

`parent_id` — один назначенный законный представитель и управляющий флагами.
`pig` касается разбития копилки этим родителем, `history` — просмотра истории,
`transaction` — переводов. Правила доступа дополнительно проверяются на сервере;
эти флаги не являются полноценной записью юридического согласия.

Предложенные технические соглашения: `age_group` = `children` для 7–13 или
`teanagers` для 14–17; `eat` = целое 0–100; `room`/`cloth` = положительные ID
каталога. Эти диапазоны и типы каталога нужно сверить с frontend-ресурсами.

### Test

`id`, `name`, `modul: string`, `level`, `questions: { "1": string }`,
`answers: { "1": string[] }`, `reward_MT`.

`modul` — тематический раздел. `questions` и `answers` имеют одинаковые ключи.
`right_answer` хранится на backend и отсутствует во всех публичных ответах,
включая вложенный `News.test`. Размер награды передаёт сервер, клиент его не задаёт.
Тест завершается один раз; начисление MT и сохранение результата должны быть атомарны.

Отдельный запрос ответа пользователя:

```json
{ "answers": { "1": 0 } }
```

Этот `answers` содержит выбранные индексы, тогда как `Test.answers` содержит
списки вариантов. Backend сверяет индексы с конкретным тестом и проверяет завершение.
DTO проверяет только форму: сам по себе он допускает пустой словарь, неизвестные
вопросы и индекс вне вариантов. Полноту ответа, существование вопросов, границы
индексов и защиту от повторной награды проверит будущий сервис.
Формат результата и критерий успешного прохождения согласуем до реализации тестов.

### Pig

`id`, `account_id`, `name`, `current_balance`, `goal_balance`.

Остатки — копейки. Backend проверяет принадлежность счёта и права на действие.
Собственный резерв не является переводом между счетами; чужое пополнение —
перевод с одновременным резервированием. Закрытие высвобождает средства на счёте владельца.

### Account

`id`, `user_id`, `balance`, `pigs: number[]`, `active_balance`, `active`,
`transactions_history: number[]`, `limit`, `limit_period`.

`user_id` всегда указывает на родителя — владельца. Детская привязка реализована
отдельно через `ChildAccountAccess` и `FamilyAccount`; она не выводится только
из `parent_id`. Поля старого `AccountRead` не переименованы.
Подробности действующего доступа — в [контракте копилок](../piggy-banks.md).

`balance` включает копилки. `active_balance = balance − сумма текущих резервов`.
Клиент не отправляет готовые остатки. `transactions_history` содержит только ID
переводов; сами операции доступны страницами через
`GET /accounts/{id}/transactions?limit=50&offset=0`.

`active: false` блокирует все финансовые изменения, включая входящие переводы.
`limit: null` и `limit_period: null` — без лимита.
`limit: 0` с заданным периодом — запрет списаний.
Период лимита календарный; учитываются исходящие переводы, включая чужие копилки,
собственный резерв в копилке лимит не расходует.
`limit` — установленный предел, а не оставшаяся сумма лимита. Frontend не должен
считать остаток лимита по неполной истории; отдельного поля с остатком лимита пока нет.

### Transaction

`id`, `cender: number`, `recipient: number`, `amount`, `data`.

`cender` и `recipient` — ID счетов, не ID пользователей. `amount` > 0.
`id` и `data` назначает сервер. Операция требует проверки действующего пользователя,
владения/доступа, обоих счетов, средств, заморозки и лимита.

### EcoFamily

`id`, `users_id: number[]`, `user_admin_id`, `name`, `accounts: number[]`.

`accounts` — явно подключённые счета. Подключение и статус администратора
сами по себе не предоставляют право распоряжения чужими средствами.

### News

`id`, `name`, `lavel`, `test_id: number|null`, `test: Test|null`, `text`.

Это учебная статья. `lavel` — возрастная группа, не сложность.
`test` — вложенный публичный объект теста, а `test_id` — его ID.
Если теста нет, оба поля `null`. Существующие названия не унифицируем с `Test.level`.

### Parent_Task

`id`, `parent_id`, `chaild_id`, `data`, `sum`, `name`, `text`.

`sum` — BYN в копейках; `data` — срок. Выполнение подтверждает `parent_id`.
Источник — выбранный родителем счёт. После успешной выплаты задание удаляется
в той же транзакции БД; при ошибке остаётся. История перевода и защита от повторной
выплаты сохраняются независимо от задания. Пользовательский статус не добавляем.
Определение счёта ребёнка ждёт решения по связи ребёнок–счёт.

### AutoTransaction

`id`, `recipient_accoun_id`, `source_account_id`, `summ`, `period`, `data`.

`summ` — BYN в копейках. Одной привязки к User недостаточно: источник сохраняется
как конкретный счёт. При недостатке денег период пропускается. Планировщик обязан
исключать повторное выполнение одной даты; эти примеры планировщик не реализуют.

## 4. Маршруты и статусы

| Метод и путь после `/api/v1` | Статус реализации | Ответ успеха |
| --- | --- | --- |
| `GET /health` | Работает | `200`, `{ "status": "ok" }` |
| `GET /me` | Работает в DEMO_MODE | `200`, User |
| `GET /accounts` | Работает в DEMO_MODE | `200`, `{ "items": [Account] }` |
| `GET /accounts/{id}` | Работает в DEMO_MODE | `200`, Account |
| `GET /accounts/{id}/transactions` | Работает в DEMO_MODE | `200`, `{ "items": [Transaction] }` |
| `POST /transactions` | Работает в DEMO_MODE | `201`, Transaction |
| `GET /news/{id}` | Проект | `200`, News |
| `GET /tests/{id}` | Проект | `200`, Test без right_answer |
| `POST /tests/{id}/submit` | Проект | Результат ещё не согласован |

Денежный запрос содержит только команду:

```json
{ "cender": 100, "recipient": 101, "amount": 2500 }
```

Форма ответа `201`; ID и время ниже условные, не обещание записи в новой БД:

```json
{
  "id": 900,
  "cender": 100,
  "recipient": 101,
  "amount": 2500,
  "data": "2026-10-20T10:30:00Z"
}
```

После успеха frontend отдельно обновляет оба доступных ему счёта и историю.
Не прибавляет и не вычитает деньги из серверного остатка как источник истины.
Автоматический повтор POST при сетевой ошибке запрещён в примере: результат
операции может быть неизвестен. Серверная идемпотентность будет отдельной частью реализации.

## 5. Ошибки

Единое тело бизнес-ошибок действующего демонстрационного API:

```json
{
  "error": {
    "code": "INSUFFICIENT_FUNDS",
    "message": "Недостаточно доступных средств",
    "details": []
  }
}
```

Статусы: `401 DEMO_USER_NOT_FOUND`, `403 DEMO_MODE_DISABLED` или `ACCESS_DENIED`,
`404 NOT_FOUND`, `409 ACCOUNT_FROZEN`, `INSUFFICIENT_FUNDS`, `LIMIT_EXCEEDED`,
`BALANCE_OVERFLOW`, `422 VALIDATION_ERROR`, `503 DATABASE_BUSY`.
Валидация возвращает безопасный список `details: [{ field, code }]` без
`input`, `ctx` и внутренних значений. Полная таблица — в
[основном контракте](../api-contract.md#ошибки).

Неизвестный маршрут возвращает `404 NOT_FOUND` с обёрткой `error`.
Клиент-пример поддерживает и `error`, и прежнюю форму FastAPI `detail`, которая
остаётся в фикстуре `error-fastapi.json` для проверки совместимости. Для UI он
использует локальные сообщения по коду. Ошибка сети — отдельный `NETWORK_ERROR`
со статусом `0`. Автоматического повторения денежного POST нет.

## 6. Сборка и разбор JSON на Python

Код проекта находится в `backend/app/schemas/wire_models.py` от корня
репозитория. Это Pydantic-схемы, не модели БД и не сервисы.
Следующий пример запускается из рабочей папки `backend`:

```python
from pathlib import Path
from app.schemas.wire_models import parse_transfer_json

# Файл → JSON → проверенный Python-объект.
raw = Path("../docs/json-exchange/examples/transfer-request.json").read_text(encoding="utf-8")
command = parse_transfer_json(raw)
sender_account_id = command.cender

# Pydantic-объект → строка для файла.
json_text = command.model_dump_json(indent=2)
Path("checked-request.json").write_text(json_text, encoding="utf-8")
```

В действующем FastAPI входной параметр типа `TransferCreate` разбирается
самим framework. Обработчик возвращает публичный DTO с `response_model` либо
`model_dump(mode="json")`. Нельзя возвращать строку `model_dump_json()` как обычный
ответ: это может превратить JSON-объект в JSON-строку с экранированными кавычками.
Нельзя принимать `balance`, `active_balance`, `MTcount`, `id` и время операции
от клиента как результаты перевода. Пример запрещает лишние поля.

## 7. Сборка и разбор на uni-app

Готовый модуль: `frontend/src/api/api.js`,
использование: `frontend/src/api/example-usage.js` (пути от корня репозитория).
Он проверяет HTTP-статус и общий тип тела (объект/массив), но не полную схему
Account/Transaction. Python-схемы проверяют типы на backend; JSON Schema в пакете
можно использовать для дополнительной проверки при разработке frontend.

```javascript
uni.request({
  url: `${apiBaseUrl}/transactions`, // действующий демонстрационный маршрут
  method: 'POST',
  header: { 'Content-Type': 'application/json' },
  data: { cender: 100, recipient: 101, amount: 2500 },
  dataType: 'json',
  success(res) {
    if (res.statusCode >= 200 && res.statusCode < 300) {
      const transaction = res.data; // уже JS-объект
      const id = transaction.id;
      // Далее обновляем данные с backend.
    } else {
      // Разбираем error/detail; готовая обёртка делает это в api.js.
    }
  },
  fail() {
    // Ошибка сети. Не повторяем денежный POST автоматически.
  }
});
```

Перед `uni.request` не нужен `JSON.stringify`, после него не нужен `JSON.parse`.
Если же вы читаете именно текст локального файла, нужен один `JSON.parse(text)`.
Проверка этого сценария находится в `frontend/tests/test-fixtures.mjs`.

## 8. Что ещё требуется согласовать

1. Детская привязка уже реализована отдельной связью `ChildAccountAccess`.
   Старые DTO `AccountRead` и `ChaildProfile` не получили переименований;
   `child_user_id` добавлен в расширенный `PigView` для действующего API копилок.
2. Флаги `agree_parent` проверяются вместе с явной привязкой счёта и семьёй;
   сами JSON-флаги доступа не предоставляют. Общий API изменения этих настроек
   и дальнейшее расширение детского банковского поведения ещё не реализованы.
3. Предложенные wire-правила дат, возрастных значений и каталога питомца,
   критерий завершения теста и календарные особенности расписания.

Для согласования формата оба разработчика используют `examples/` и `schemas/`.
Действующий API описан в [основном контракте](../api-contract.md),
`/openapi.json` и Swagger `/docs`. Наличие структуры в `entities.json` само по
себе не означает наличие маршрута: учебные функции, задания, питомец,
автопереводы, настройка лимитов и заморозка пока ждут реализации.
Действия с копилками доступны по [новому контракту](../piggy-banks.md).
