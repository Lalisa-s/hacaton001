# Копилки: действующий API и правила

Префикс — `/api/v1`, режим — `DEMO_MODE=true`. Суммы передаются целыми копейками
BYN: `500` означает 5,00 BYN. Списки имеют форму `{ "items": [...] }`.
Названия прежних полей, включая `ChaildProfile`, сохранены. Новые публичные
схемы находятся в `backend/app/schemas/pigs.py`, маршруты — в
`backend/app/api/v1/endpoints/pigs.py`.

## Демонстрационные участники

| Переключатель в интерфейсе | `X-Demo-User-Id` | Доступные счета | Назначение |
| --- | --- | --- | --- |
| Родитель | `10` | `100`, `101` | Назначенный `parent_id` ребёнка `20` |
| Ребёнок | `20` | Явно подключённый `101` | Свои копилки, пополнение, запрос на разбитие |
| Участник семьи | `11` | `110` | Другой родитель той же семьи; может пополнять копилку |

Все три пользователя входят в семью `1`. Законный владелец счетов `100` и `101`
остаётся родителем `10`: детский доступ к `101` задан отдельной связью
`ChildAccountAccess`, а подключение к семье — `FamilyAccount`. Участие в семье
само по себе не даёт права списывать деньги с чужого счёта.

На новой БД: `100.balance=20000`, `101.balance=10000`, `110.balance=15000`.
Копилка `500` («Велосипед») связана со счётом `101` и ребёнком `20`, имеет
`current_balance=3000`, `goal_balance=30000`. Доступно на `101` — `7000`.
Повторный запуск сохраняет существующие суммы, имена, разрешения и запросы.

Переключатель выбирает демонстрационную запись, **это не аутентификация**.
`src/api/client.js` сохраняет выбор локально и добавляет `X-Demo-User-Id` в запросы.
Веб-интерфейс обращается к `/api/v1/...` на том же origin; Vite проксирует `/api`
на backend. При ручном запросе без заголовка используется `DEMO_USER_ID`.
Настоящие банковские операции и персональные данные в этом демо не используются.

## Что означает баланс копилки

У карточки копилки один денежный остаток — `current_balance`. Он зарезервирован:
из копилки нельзя выполнить обычный перевод или покупку. `goal_balance` — цель,
а не второй доступный баланс. Достижение цели не закрывает копилку автоматически.

Для счёта сервер вычисляет:

```text
active_balance = balance − сумма current_balance всех копилок счёта
```

`balance` включает резерв. Веб-карточка обычного счёта показывает доступные
деньги; копилки отображаются отдельными карточками. Готовые остатки клиент
никогда не отправляет на сервер.

При разбитии `current_balance` становится `0`, `closed` — `true`.
`Account.balance`, владелец и привязка счёта не меняются: деньги остаются на
счёте-владельце и становятся доступными для трат. Нового перевода при этом нет.
Закрытая копилка и рассмотренные запросы сохраняются в SQLite.

## Маршруты

| Метод и путь после `/api/v1` | Тело | Успешный ответ |
| --- | --- | --- |
| `GET /pigs` | — | `200`, `{ "items": [PigView] }` |
| `POST /pigs` | `PigCreate` | `201`, `PigView` |
| `PATCH /pigs/{pig_id}` | `{ "name": "..." }` | `200`, `PigView` |
| `POST /pigs/{pig_id}/contributions` | `{ "account_id": 110, "amount": 500 }` | `200`, `PigView` или `PigContributionReceipt` |
| `POST /pigs/{pig_id}/break-requests` | `{}` | `201`, `RequestView` |
| `POST /pigs/{pig_id}/break` | `{}` | `200`, `PigView` |
| `GET /pig-break-requests` | — | `200`, `{ "items": [RequestView] }` |
| `POST /pig-break-requests/{request_id}/approve` | `{}` | `200`, `RequestView` |
| `POST /pig-break-requests/{request_id}/reject` | `{}` | `200`, `RequestView` |
| `GET /family/members` | — | `200`, `{ "items": [FamilyMemberView] }` |

Для команд без параметров отправляется именно JSON `{}`. Лишние поля запрещены.
ID — положительные безопасные целые JavaScript, максимум `9007199254740991`.
Суммы пополнения и цель — строго положительные целые в том же диапазоне.

## Создание, имя и просмотр

Копилку создаёт ребёнок для себя либо его назначенный `parent_id`:

```json
{
  "account_id": 101,
  "child_user_id": 20,
  "name": "Велосипед",
  "goal_balance": 30000
}
```

Счёт должен быть активен, явно подключён к ребёнку и той же семье, а его
владелец должен совпадать с `parent_id`. Новая копилка начинается с нуля.
Имя — строка от 1 до 100 символов после удаления пробелов по краям.
Переименование доступно этому ребёнку и его `parent_id`, пока копилка открыта.

Начальный `PigView` копилки `500`:

```json
{
  "id": 500,
  "account_id": 101,
  "name": "Велосипед",
  "current_balance": 3000,
  "goal_balance": 30000,
  "child_user_id": 20,
  "parent_id": 10,
  "closed": false,
  "pending_request_id": null
}
```

Ребёнок получает через `GET /pigs` только свои копилки. Родители видят копилки
своей семьи, но изменить имя и разбить чужую детскую копилку без назначения
`parent_id` не могут. `GET /family/members` возвращает только
`id`, `login`, `role`, `parent_id`, `accounts` — без балансов, истории и паролей.
`accounts` здесь содержит ID счетов, явно подключённых к семье и доступных
соответствующему участнику; это не разрешение списывать с них другому участнику.

## Пополнение

Пополнять могут участники той же семьи с разрешённых им счетов. Оба счёта должны
быть явно подключены к семье. Родитель использует свой счёт; ребёнок — явно
подключённый к нему родительский счёт при включённом `agree_parent.transaction`.
Обычный `POST /transactions` ребёнку недоступен: для копилки используется
только `/pigs/{pig_id}/contributions`.

- Если `account_id` совпадает со счётом копилки, меняется только резерв.
  Общий баланс счёта прежний, доступный уменьшается. Перевод не создаётся,
  лимит исходящих переводов не расходуется.
- Если счета различаются, выполняется перевод на счёт-владелец с одновременным
  увеличением резерва. Он появляется в истории и учитывает лимит источника.
  Доступный остаток получателя от такого пополнения не увеличивается.
- Недостаток доступных средств, замороженный источник или получатель,
  превышение лимита и переполнение отклоняют операцию целиком.

Для своей детской копилки и для родителя ответ — полный `PigView`.
Ребёнок также может пополнить чужую детскую копилку той же семьи по сообщённому
номеру, но не получает её имя, владельца, цель или остаток. Его ответ:

```json
{ "pig_id": 500, "amount": 500 }
```

Это `PigContributionReceipt`. Клиент проверяет вариант ответа: наличие
`current_balance` означает `PigView`; квитанцию нельзя использовать как полную
обновлённую карточку чужой копилки.

## Запрос на разбитие и решение родителя

Ребёнок отправляет запрос только для своей открытой копилки. Пока запрос
`pending`, копилка остаётся открытой и весь резерв сохраняется. Повтор команды
для той же открытой копилки возвращает существующий pending-запрос с тем же ID.

```json
{
  "id": 1,
  "pig_id": 500,
  "child_user_id": 20,
  "parent_id": 10,
  "status": "pending",
  "created_at": "2026-10-21T09:00:00Z",
  "resolved_at": null
}
```

ID и время в примере условные. `created_at` и `resolved_at` — UTC ISO 8601 с `Z`.
Ребёнок видит свои запросы; родитель — адресованные ему как `parent_id`.

Только назначенный `parent_id` при включённом `agree_parent.pig` может:

- `approve`: атомарно разбить копилку и установить запросу `approved`;
- `reject`: установить `rejected`, сохранив резерв и открытую копилку;
- разбить копилку напрямую через `/pigs/{pig_id}/break`, без запроса ребёнка.

У рассмотренного запроса заполнен `resolved_at`. Повтор `approve` или `reject`
возвращает `409 REQUEST_ALREADY_RESOLVED`; резерв повторно не освобождается.
Таким образом, эффект подтверждения выполняется ровно один раз. Это не общая
идемпотентность любых денежных POST. При прямом разбитии оставшиеся pending-запросы
закрываются как `rejected`, поскольку решение выполнено вне их `approve`.

Изменение резервов, переводов и статусов выполняется транзакционно. SQLite
получает блокировку записи до финансовых проверок. Запрос, копилка и остатки
сохраняются между перезапусками. Автоматически повторять пополнение после
сетевой ошибки нельзя: сначала перечитайте доступные данные и проверьте результат.

## Ошибки

Используется обёртка `error` из [основного контракта](api-contract.md#ошибки).
Дополнительно для копилок:

| HTTP | `error.code` | Причина |
| --- | --- | --- |
| `403` | `ACCESS_DENIED` | Чужая копилка/счёт, другая семья, неподходящий `parent_id` или отключённое разрешение |
| `404` | `NOT_FOUND` | Копилка, счёт, профиль ребёнка или запрос не найдены |
| `409` | `PIG_CLOSED` | Копилка уже разбита |
| `409` | `REQUEST_ALREADY_RESOLVED` | Запрос уже рассмотрен |
| `409` | `INVALID_RESERVE` | Резерв больше общего остатка счёта |
| `409` | `ACCOUNT_FROZEN` | Финансовое действие затрагивает замороженный счёт |
| `409` | `INSUFFICIENT_FUNDS`, `LIMIT_EXCEEDED`, `BALANCE_OVERFLOW` | Финансовая проверка не пройдена |
| `422` | `VALIDATION_ERROR` | Неверное тело, тип или значение |
| `503` | `DATABASE_BUSY` | Не удалось получить блокировку записи |

Для создания и пополнения нужны активные счета; разбитие и approve требуют
активного счёта копилки. Переименование, запрос ребёнка и reject сами по себе
деньги не изменяют.

## Короткая проверка через PowerShell

После запуска backend, на новой БД:

```powershell
$apiBaseUrl = 'http://127.0.0.1:8000/api/v1'
$familyActor = @{ 'X-Demo-User-Id' = '11' }
$childActor = @{ 'X-Demo-User-Id' = '20' }
$parentActor = @{ 'X-Demo-User-Id' = '10' }

Invoke-RestMethod "$apiBaseUrl/pigs" -Headers $childActor
$contributionJson = @{ account_id = 110; amount = 500 } | ConvertTo-Json -Compress
Invoke-RestMethod "$apiBaseUrl/pigs/500/contributions" -Headers $familyActor -Method Post -ContentType 'application/json' -Body $contributionJson
$breakRequest = Invoke-RestMethod "$apiBaseUrl/pigs/500/break-requests" -Headers $childActor -Method Post -ContentType 'application/json' -Body '{}'
Invoke-RestMethod "$apiBaseUrl/pig-break-requests/$($breakRequest.id)/approve" -Headers $parentActor -Method Post -ContentType 'application/json' -Body '{}'
Invoke-RestMethod "$apiBaseUrl/accounts/101" -Headers $parentActor
```

После одного пополнения на `500` копеек и подтверждения: `110.balance=14500`,
`101.balance=10500`, `101.active_balance=10500`, у копилки `current_balance=0`
и `closed=true`. Этот сценарий изменяет демо-БД; закрытую копилку повторно
пополнить нельзя. Для новой попытки создайте новую копилку.

На экране тот же сценарий выполняется переключателем демонстрационного профиля,
карточкой копилки и списком родительских запросов. Новых Python/npm-зависимостей
для этой функции не добавлено. Учебные модули, питомец, задания, автопереводы,
настоящий вход и банковская интеграция остаются отдельной будущей работой.
